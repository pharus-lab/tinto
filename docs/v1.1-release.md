# Tinto v1.1 release readiness

This is the release checklist and evidence record for the built-in Harper integration. A checklist item is complete only when its result has been recorded against the exact source revision and artifact tested.

## Release decisions

- **v1.1 targets macOS on Apple silicon.** Linux release validation is deferred to actual Linux computers. Do not publish Linux installers as part of v1.1 on the strength of the previous container tests.
- Keep the official `harper.js` **3.2.0** package. Do not build a newer Harper engine from source just to obtain a JavaScript release.
- Bundle English and UK English spelling/grammar and Spanish spelling. French is not offered or downloaded; legacy documents remain editable with their original language metadata.
- Automatic spelling and grammar checks start off and are independent. Every correction requires individual acceptance and remains undoable. This release adds no rewriting or style advice.
- Drive remains experimental behind `TINTO_EXPERIMENTAL=1`; live Google-account validation is still outstanding.
- Linux can follow as **v1.1.1** when the changes are compatible packaging/platform fixes, or **v1.2.0** when the release also introduces new features. Use three-part semantic versions; do not use `1.2.0.0`.
- This is a one-time release validation effort, without a new CI workflow. Publishing the release remains a separate action.

### Repeat the macOS release checks

Run `npm run package -- darwin arm64`, followed by `npm run dmg`. The DMG script checks the already-built version, architecture, signature, source archive, and image integrity. It preserves existing installers and writes each release to its own version directory. It arranges the installer window through Finder, which may ask permission the first time. No Linux package is produced by this sequence.

Mount both release images read-only and set the executable paths below to the mounted apps. The upgrade regression requires the previous app to be **1.0.0** and the current app to match `package.json`.

```sh
TINTO_PREVIOUS_EXECUTABLE="/path/to/v1.0-volume/Tinto.app/Contents/MacOS/Tinto" \
TINTO_PACKAGED_EXECUTABLE="/path/to/v1.1-volume/Tinto.app/Contents/MacOS/Tinto" \
node --test --test-concurrency=1 \
  tests/desktop.test.mjs tests/exchange.test.mjs tests/navigation.test.mjs \
  tests/writing-desktop.test.mjs tests/typography.test.mjs tests/authorship.test.mjs \
  tests/publish.test.mjs tests/site-guide.test.mjs tests/release-upgrade.mjs
```

Then run `shasum -a 256 -c SHA256SUMS.txt` inside the new release directory and again inside the original v1.0 release directory. Detach both images after testing. Publishing remains a separate action and must include the DMG, checksum file, and corresponding Pandoc source archive.

## Linux validation deferred to actual Linux

No Linux v1.1 release readiness is claimed. The earlier Ubuntu 24.04 container checks covered only part of the application; amd64 used emulation and the test launcher disabled Chromium sandboxing. They do not establish ordinary desktop, keyring, Wayland, or physical GPU compatibility.

The following preparation is present in source but remains **unverified on Linux**: branded launcher/window icons, desktop identification, Debian prerelease ordering, updated package description, sandbox-enabled installed-app fixtures, consistent isolated keyring mocks, and expanded installed-app suite selection. These changes require the full checks below before distribution.

### Build and install the exact candidate

1. Freeze the source revision and lockfile shared with the macOS comparison build. Include any uncommitted changes in the recorded source snapshot/hash.
2. Run `npm ci`, `npm run typecheck`, and `npm test` on native Linux for each architecture. Install Playwright Chromium with `npx playwright install chromium`, or use `CHROME_PATH`; run desktop tests within a graphical session.
3. Build with `npm run package -- linux x64` or `npm run package -- linux arm64`, then `sh scripts/linux-deb.sh amd64` or `sh scripts/linux-deb.sh arm64`.
4. Development packages use names such as `out/development/tinto_1.1.0~dev.0_amd64.deb`. The app retains its SemVer development version; only Debian metadata/filenames use `~`. Final release filenames use their final three-part version.
5. Install the matching package using `sudo apt install ./path/to/tinto_VERSION_ARCH.deb`. Validate the stock graphical installer where available; document the terminal installation route accurately.
6. As the normal signed-in desktop user, run `sh scripts/linux-smoke.sh` from the matching source checkout. It requires the installed version to match, selects all eight existing desktop-bearing suites, and uses sandbox-enabled Electron launches. It does not create a desktop session or replace the native checks below.
7. Record all results and expected platform skips. Add native Linux lifecycle and real-keyring regressions where the existing tests use macOS-only behavior or mocks.

### Linux release gate

Every applicable functional test must pass on the supported matrix. The two macOS-only desktop tests are expected skips on Linux and need Linux lifecycle counterparts. Launch failures, data corruption/loss, insecure credential storage, and broken core workflows block distribution. Record minor limitations explicitly.

For each fix, re-run its regression and affected suites; re-run macOS checks when shared behavior changes. Produce final package SHA-256 checksums, evidence logs/screenshots, the completed matrix, and accurate README installation/update instructions. Choose v1.1.1 or v1.2.0 according to the final release contents, then seek release publication through the normal release process.
